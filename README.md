#### 1.2 AI 在软件开发中的优势

AI 在软件开发中的主要价值，是在目标、上下文、接口和验证标准相对明确时，提高局部任务的完成效率。它不是独立的软件负责人，而是可以快速执行、快速反馈的协作者。

AI 的优势主要体现在以下方面：

1. **快速完成边界明确的实现任务**  
   当输入输出、接口契约、数据结构和验收标准已经明确时，AI 可以高效生成样板代码、业务函数、测试草稿、文档草稿和重构方案。

2. **辅助方案比较和技术讨论**  
   在需求相对清楚的情况下，AI 可以提出多种实现思路，帮助开发者比较复杂度、可维护性、扩展性和潜在风险。

3. **处理重复性和模式化工作**  
   对于类型定义、接口封装、数据转换、错误处理、配置生成、基础测试等结构清晰的任务，AI 通常能提供稳定的辅助。

4. **辅助理解代码和定位问题**  
   AI 可以帮助解释已有代码、梳理调用链、分析错误日志、推测可能原因，并提醒开发者关注边界情况。

5. **支持文档维护和经验沉淀**  
   AI 可以把零散记录整理成结构化文档，也可以辅助生成接口说明、验收步骤、变更记录和协作规范。

6. **执行清晰目标下的重构任务**  
   当人类已经指出问题和重构目标时，AI 可以较好地执行模块拆分、命名整理、重复代码消除和局部结构优化。


#### 1.3 AI 在软件开发中的局限

AI 不能被视为项目责任主体，也不能替代人类完成关键判断。它的输出必须经过审查、验证和必要的修正。

AI 的局限主要包括：

1. **不能承担需求和责任判断**  
   AI 不真正理解项目的业务责任、课程要求、用户风险和长期维护成本，不能替代人类决定“应该做什么”“为什么做”以及“做到什么程度”。

2. **容易受上下文和已有代码影响**  
   AI 会模仿当前代码风格，包括不良模式。如果仓库中存在命名混乱、重复代码或临时写法，AI 可能继续复制并放大这些问题。

3. **可能生成不准确或不可运行的内容**  
   AI 可能编造不存在的 API，误解项目上下文，忽略已有架构约束，或者给出看似合理但无法通过验证的实现。

4. **不能天然保证工程质量**  
   AI 生成的代码不必然满足安全性、隐私保护、性能、可维护性和可测试性要求。涉及用户数据、密钥、网络请求、文件读写和权限控制时，必须由人类严格审查。

5. **对复杂环境和依赖问题判断不足**  
   当问题来自框架缺陷、版本差异、运行环境、第三方依赖或系统级行为时，AI 可能倾向于在现有代码里绕过问题，而不是识别真正的外部约束。

6. **对并发、异步和跨模块协同问题更容易失误**  
   多线程、多进程、异步任务、资源释放、状态同步等问题通常难以复现和验证，AI 在这类场景中需要更明确的日志、测试和人工判断。

7. **缺乏主动的领域洞察和产品判断**  
   AI 能识别现象，但不一定能判断某个“正常现象”是否应该优化。领域知识、工程直觉和产品取舍仍然是人类的核心责任。

8. **不能替代最终验收**  
   架构取舍、隐私边界、数据结构设计、用户体验判断和最终验收必须由人类负责。AI 可以辅助分析和生成方案，但不能代替项目成员承担最终决策。

因此，在 AI 协作开发中，更合理的定位是：**AI 是高效率协作者，不是项目负责人；人类是定方向、审代码、做判断的驾驶员。**

### 第5章 代码生成与审查

本章关注如何让 AI 辅助生成代码，以及如何对 AI 生成的代码进行审查。AI 可以帮助生成函数、类、接口、页面组件、数据处理逻辑、测试草稿和重构方案，但生成结果不能直接等同于可合并代码。

本章建议包括：

- 明确生成目标：说明要实现什么功能、输入输出是什么、不能修改哪些模块。
- 提供上下文：给出相关接口、数据结构、现有代码风格和约束条件。
- 分批生成代码：优先让 AI 完成边界清晰的小任务，而不是一次生成整个系统。
- 审查正确性：检查代码是否满足需求，是否处理异常情况，是否存在明显逻辑漏洞。
- 审查一致性：检查命名、目录结构、接口格式、错误处理和代码风格是否与项目已有规范一致。
- 审查安全性：检查是否泄露密钥、是否直接信任用户输入、是否绕过权限或隐私约束。
- 审查可维护性：检查是否过度设计，是否引入不必要依赖，是否让简单逻辑变复杂。
- AI 会盲目复制代码风格，所以必须定期 code review

### 第6章 测试与检验

本章关注如何验证 AI 生成或修改后的代码是否真正可用。测试与检验不只包括自动化测试，也包括人工操作、边界输入、异常路径和回归验证。

本章建议包括：

- 编译与构建检查：确认项目能够正常编译、打包或启动。
- 类型与静态检查：使用项目已有工具检查类型错误、格式问题和潜在代码质量问题。
- 单元测试：验证单个函数、类或模块在不同输入下是否符合预期。
- 集成测试：验证多个模块组合后是否能够正确协作。
- 端到端测试：从用户视角验证一条完整操作流程是否成立。
- 边界场景测试：验证空数据、重复数据、无效输入、超长输入、网络失败、权限不足等情况。
- 手动验收记录：记录测试环境、操作步骤、输入数据、预期结果、实际结果和遗留问题。
- 验证方案是架构之外最重要的 harness 机制。

### 第7章 排错 Debugging

本章关注如何借助 AI 更高效地定位和修复问题。排错时不能只描述“报错了”，而应尽量提供可复现信息，让 AI 能够基于事实分析问题。

本章建议包括：

- 收集错误信息：包括错误日志、报错截图、失败命令、状态码、异常堆栈等。
- 复现问题：记录从正常状态到触发错误的具体步骤。
- 缩小范围：判断问题来自输入数据、业务逻辑、接口调用、依赖环境、配置文件还是外部服务。
- 检查最近改动：对比问题出现前后的代码变化，优先排查最近修改过的模块。
- 验证假设：一次只修改一个可能原因，避免同时改动过多导致无法判断真实原因。
- 修复后回归：确认原问题消失，并重新测试相关功能，避免修复一个问题又引入另一个问题。
- 反馈质量决定 AI 修复效率：不要只说有问题，要给日志、预期和复现步骤。

### 第8章 文档维护

本章关注如何在 AI 协作开发中保持文档与代码同步。文档不是开发结束后的补充材料，而是需求澄清、任务分工、接口约束和后续维护的重要依据。

本章建议包括：

- README 维护：说明项目目标、运行方式、核心功能、目录结构和基本使用流程。
- 需求文档维护：记录功能目标、用户场景、边界条件和不做什么。
- 架构文档维护：记录模块划分、调用关系、数据流向和关键技术选择。
- 接口文档维护：记录接口名称、参数、返回值、错误格式和调用示例。
- 测试文档维护：记录自动化测试、手动验收步骤、测试数据和已知问题。
- 变更记录维护：说明每次重要修改的原因、影响范围和验证结果。
- 命名与归档：将临时记录整理成有意义的文件名，避免长期保留含义不清的草稿文件。
- 记录关键决策和状态，不记录无价值过程细节，并在里程碑后更新文档。

### 第10章 封闭式自动化检验实战

*预设标准答案，通过 Test Case（测试用例）严格检验 AI 生成代码或 Prompt 的逻辑严密性与格式稳定性。*

#### 实战一：日常场景的复杂逻辑与结构化提取（水果店计费系统）

* **场景：** 编写一段高阶提示词（Prompt），让 AI 处理自然语言输入（如：“草莓3斤，需要果切，节日期间，需要环保袋”），并根据以下严格规则计算费用：
1. **阶梯与条件折扣：** 苹果8元/斤、草莓22元/斤、葡萄15元/斤。满3斤同种水果打9折并向下取整。
2. **附加服务费：** 果切费2元/斤（按总斤数计）。
3. **特殊溢价：** 节日期间，水果费与果切费合计后加收20%，并向上取整。
4. **固定耗材：** 环保袋2元。


输入：一段自然语言输入

输出：JSON输出，仅两个字段———仅输出包含 `total_bill`（最终总价）和 `fruit_cost`（节假日加价前的折后水果费）两个字段的标准 JSON 字符串，过滤任何多余的解释性废话（幻觉控制）。

* **检验与难点：** * **运算次序与精度控制：** 检验 AI 能否严格遵循“折扣向下取整 $\rightarrow$ 叠加服务费 $\rightarrow$ 溢价向上取整 $\rightarrow$ 叠加耗材”的先后顺序计算。

* **自动化测试：** 编写 Python 检验脚本，批量输入不同的顾客购买描述，解析返回的 JSON 并与人工预设的正确金额进行断言比对（Assert）。

### 实战二：动态寻优与分段逻辑提取（网约车计费系统）

* **场景：** 编写一段高阶提示词（Prompt），让 AI 处理包含时间、里程、优惠和附加费用的自然语言输入（如：“昨晚11点半打车回家，一共跑了14公里，交了10块钱过路费，账户里有一张满40减8元的券和一张75折券”），并根据以下严格规则计算最优费用：

1. **分段里程计费：** * 起步价 13元（包含前 3公里）。
* 超出起步里程部分：3 到 10公里（含）按 2.5元/公里计费；超过 10公里的远途部分按 3.5元/公里计费（远途加价）。


2. **时段浮动费率：** * 若出发时间处于夜间（23:00 - 06:00），计算出的**纯里程费**（不含起步价）需要加收 20% 的夜间服务费，且该部分计算结果**向上取整**。
3. **动态折扣（互斥原则）：** * 将起步价与最终里程费相加得到“基础车费”。
* 若用户同时拥有“满减券”和“折扣券”，系统需自动比较两种优惠方案，**强制选用对用户最划算（最终车费最低）的方案**。折扣后的车费**向下取整**。


4. **固定附加费：** * 高速费、停车费等附加费用**不参与任何折扣**，在最终扣款时直接原价叠加。

* **输入：** 一段包含打车里程、时间、路桥费及可用优惠券的自然语言描述。
* **输出：** 标准 JSON 字符串，仅包含以下三个字段，绝对过滤任何解释性废话：
* `total_fare`（最终需支付的总金额）
* `base_fare`（打折前的基础车费总额，不含附加费）
* `applied_discount`（实际生效的优惠策略，输出字符串如 "满40减8" 或 "75折"）


* **检验与难点：** * **逻辑分叉与寻优能力：** 检验 AI 是否具备“分支计算并比较”的能力（AI 必须在隐式思维过程中同时计算满减和打折的结果，比较大小后才能得出 `applied_discount`）。
* **作用域陷阱：** 检验 AI 是否能精准区分各类费用的作用域（夜间加价**仅**针对超出的里程费；打折**仅**针对基础车费，绝对不能把过路费也打折）。
* **自动化测试挑战：** 编写 Python 测试脚本，构造极具迷惑性的 Edge Case。例如：某一里程下，满减和打折的最终金额完全一致，测试 AI 的边界处理机制；或者总里程为 2.5公里（未超起步价），测试 AI 是否会错误计算负数里程。



#### 实战三：算法性能与边界控制（组合数学与模运算求解器）

* **场景：** 编写一段高阶提示词（Prompt），要求 AI 编写一个结合模运算的高效 Python 求解算法，解决特定的组合数学问题：

1. **核心逻辑（整数划分与排列）：** 计算将 $n$ 个相同物品划分为 $k$ 个非空组的方案数，随后将结果乘以 $m$ 个不同物品的全排列数。
2. **模运算约束：** 由于组合数结果极大，要求在动态规划的每一次状态转移（加法）以及最终的乘法步骤中，严格对 $10^9 + 7$ 取模。
3. **性能要求：** 针对大数据范围（ $n \le 1000$ , $m \le 10^5$），强制要求 AI 使用空间复杂度优化的动态规划（如一维滚动数组），避免内存溢出或计算超时。

* **输入：** 三个正整数参数  $n$ 、 $k$ 、 $m$ 。
* **输出：** 纯代码输出——仅输出一个名为 `solve(n, k, m)` 的 Python 函数代码块。强制要求过滤任何 Markdown 标记（如 ````python`）、导入语句以外的多余代码，以及解释性废话（幻觉控制）。
* **检验与难点：** * **算法底座与同余定理：** 检验 AI 是否能写出正确的时间复杂度为 $O(n \cdot k)$ 的 DP 状态转移方程，并排查其是否在中间计算环节遗漏了取模操作（防止 Python 隐式处理超大整数导致性能急剧下降）。
* **自动化测试（OJ 判题模拟）：** 编写本地测试脚本（类似 LeetCode 的判题机），通过 `exec()` 或动态导入的方式加载 AI 生成的函数，批量传入极端边界测试用例（如 $n=1000, k=500, m=99999$）。一方面使用断言（Assert）比对计算结果的正确性，另一方面严格限制并监控函数的执行时间（如必须在 1 秒内跑完）。
